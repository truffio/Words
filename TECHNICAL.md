# Words: Technical Considerations and Implementation Plan

*Implementation guidelines and delivery plan for the Words English vocabulary game. For the educational concept and gameplay, see [WORDS.md](WORDS.md).*

---

## 1. Purpose and Design Principles

### Design Priorities

- **Open a URL in a browser and play**, on a laptop/PC first and on an iPad later. No app installation or account.
- **No backend**, database, or persistent learning history in the initial version.
- **Consistent AI-generated artwork:** each room is painted as **one complete illustration**, then split into interactive objects by a build script. **No scene editor is required.**
- **High-quality prerecorded audio**, with no speech synthesis required during play.
- **Scale target:** approximately **12 rooms** and **50 interactive objects per room** (~600 vocabulary entries, fewer once shared words such as *chair* or *table* are counted once).
- **Keep game rules independent** of artwork and scene layout.

### Target Platform

- **First: laptop/PC.** Current desktop browsers (Chrome, Edge, Firefox, Safari), mouse or trackpad, physical keyboard. This is the platform for development, testing, and early play, from M1 onward.
- **Later: iPad.** Safari on a recent iPad (iPadOS), **landscape** orientation, touch input. Added in **M5** (§10).
- **Input is written once for both.** The game uses Phaser's unified pointer events, so a mouse click and a finger tap follow the same code path. iPad work is about browser specifics (§7), not rewriting input.

### Engineering Principles

- **Rules are plain JavaScript.** Question selection, answer checking, scoring, and hit lookup live in modules with **no Phaser or DOM dependency**, so they can be unit-tested in Node.
- **Randomness is injectable.** All shuffling uses a seedable random generator so tests and bug reports are reproducible.
- **Content is data.** Adding a room means adding a painting, masks, audio, and a manifest, with no changes to game code.
- **Layout is generated, not hand-placed.** Object positions, sprites, and click regions are derived automatically from the room painting and its masks.

## 2. Technology Stack

| Area | Choice | Notes |
|------|--------|-------|
| **Runtime / game** | **Phaser 4** (JavaScript) | Renders the room in an HTML canvas (WebGL, with Canvas fallback) and handles loading, scaling, audio, and animation. Phaser 4 has been stable since April 2026. Phaser 3.90 (May 2025) is the final 3.x release, so a new project should start on 4.x. |
| **Web shell** | HTML and CSS | Start screen, room selection, HUD (score, attempts, timer), round summary, and the spelling input field. See §3. |
| **Room build pipeline** | Node.js script (`tools/build-rooms`) using **sharp** for image processing | Turns each room's painting and object masks into a background, an object sprite atlas, a **hit map**, and a layout file. Replaces a visual scene editor. See §4–§5. |
| **Mask authoring** | Interactive segmentation tool and/or layered image editor (Krita, GIMP, Photoshop) | One black-and-white mask per object instance, exported as PNG at the painting's resolution. Any image editor is enough for M1; the final tool is chosen in M2 (§11). |
| **Artwork** | AI-generated room illustrations | One full painting per room at the logical resolution (2048 × 1536). Inpainting is used to add or fix individual objects. Shipped as WebP. |
| **Audio** | High-quality text-to-speech, generated **offline** | Generated by a script from the vocabulary data and exported as **mono MP3**. Played back with Phaser's Web Audio sound manager. Browsers require a first click or tap before playing audio (see §7). |
| **Configuration** | JSON, validated with **JSON Schema (Ajv)** | Shared lexicon, room manifests, and exercise settings. |
| **Development tooling** | Node.js (LTS), npm, **Vite** | Dev server (reachable from an iPad on the local network from M5), production build, and scripts. Start from Phaser's official Vite project template. |
| **Code quality** | ESLint + Prettier | JavaScript with JSDoc type annotations; optionally `checkJs` for editor type-checking. |
| **Unit tests** | Vitest | Question selection, answer checking, scoring, session state, hit-map lookup, room-build algorithms, and manifest validation. |
| **Browser tests** | Playwright | Gameplay interactions in desktop **Chromium** from M1; **WebKit with an iPad device profile** (closest to iPad Safari) added in M5. Screenshots on failure. |
| **Continuous integration** | GitHub Actions | On push and pull request: lint, content validation, unit tests, room build, production build, end-to-end tests. |

> **Deployment is deliberately outside the initial scope.** The build output is a static folder that any static host can serve later. Until then, the game is played from the Vite dev or preview server: in a browser on the development machine, and from M5 on the iPad over the local network.

> **Licensing to confirm before production:** the commercial-use terms of the chosen AI image generator and TTS provider, and the license of any segmentation tool used. Phaser and sharp are open source (MIT and Apache-2.0).

## 3. Runtime Architecture

The application is a **static website**: HTML, JavaScript, CSS, image files, audio files, and room/configuration data. **All game execution happens in the child's browser.**

### Layers

```
┌────────────────────────────────────────────────────────────┐
│  Shell (HTML/CSS)  start · room select · HUD · summary ·   │
│                    spelling input · rotate-device notice   │
├────────────────────────────────────────────────────────────┤
│  Game (Phaser 4)   Boot · Preload · generic RoomScene ·    │
│                    input · highlight/feedback · audio      │
├────────────────────────────────────────────────────────────┤
│  Core (plain JS)   lexicon/manifest model · hit lookup ·   │
│                    question selection · answers · session  │
└────────────────────────────────────────────────────────────┘
          ▲ Core never imports Phaser or the DOM.
```

- There is **one generic `RoomScene`**. It builds any room at runtime from that room's generated layout file, so no room needs its own code.
- The **shell** and the **game** both talk to the **core** through a small event interface (e.g. `challengeStarted`, `answerEvaluated`, `roundEnded`).
- The HUD lives in the **DOM**, not the canvas. It is crisp at any scale, easy to style, and Playwright can read it directly (e.g. assert the correct-answer counter text).

### Core Responsibilities

| Component | Layer | Responsibility |
|-----------|-------|----------------|
| **Application shell** | Shell | Start the game (also unlocks audio), select a room and activity, show instructions, HUD, and round summary. |
| **Scene manager** | Game | Load and display the selected room; transition to another room. |
| **Asset manager** | Game | Load the selected room's background, atlas, hit map, layout, and audio; release room-specific resources when leaving. |
| **Hit lookup** | Core | Convert a tap in logical coordinates into an **instance**, and from it an **object ID**, using the room's hit map (§4). Pure function over a byte array. |
| **Interaction layer** | Game | Convert pointer/touch screen coordinates to logical coordinates, call the hit lookup, and show selection and feedback. |
| **Exercise controller** | Core | Choose the target vocabulary, produce the prompt, evaluate the answer, decide retry / reveal / advance. |
| **Session state** | Core | Score, attempts, current room, activity, active challenge, and optional elapsed time, **in memory only**. Reloading the page starts fresh. |
| **Audio player** | Game | Play cached prerecorded word, prompt, and feedback clips on demand; never overlap two prompts. |
| **Test bridge** | Game | Test builds only (see §8). Exposes the current challenge and each instance's tap point. |

### Illustrative Event Flow (Listen and Find)

1. The child taps **Start** (unlocking audio), then chooses **Kitchen**.
2. The game loads the kitchen background, atlas, hit map, layout, manifest, and the kitchen's audio clips.
3. The exercise controller selects an object ID, e.g. `refrigerator`.
4. The shell shows *"Find the refrigerator."* and the audio player plays the matching prompt clip.
5. The child taps the screen. The interaction layer converts the point to logical coordinates, and the hit lookup returns `refrigerator` (or nothing for walls, floor, and decorative details).
6. The controller compares IDs and returns a result: *correct*, *try again*, or *reveal* (see §4).
7. The game plays feedback (e.g. glow and pulse on the object's sprite), the HUD updates, and the next challenge starts. After the last challenge, the summary appears.

## 4. Scene and Content Model

### Painted Room + Masks

Each room starts from **one painting** in which every object is already drawn in place. For every interactive object instance, a **mask** marks the pixels belonging to it. The room build script derives everything else:

```
 room.png  +  masks/*.png  +  manifest.json
        │
        ▼   npm run build:rooms
 ┌─────────────────────────────────────────────────────────────┐
 │ background.webp   the full painting, objects included       │
 │ objects.json +    multi-atlas of object cut-outs and white  │
 │ objects-<n>.webp  glow halos, pages ≤ 2048 × 2048           │
 │ hitmap.bin        instance index per pixel (0=none), RLE    │
 │ layout.json       per instance: objectId, bounds, hit       │
 │                   bounds, tap point, cut-out frame          │
 └─────────────────────────────────────────────────────────────┘
   + reports/rooms/<room>-debug-hits.png   review image (not shipped)
```

`build:rooms` runs the same checks as `npm run validate:content` first (shared code in `tools/lib/room-content.js`) and stops on any problem. The review image is written outside `public/` so it never ends up in the game build.

- **The background keeps the objects.** Cut-out sprites are drawn exactly over their own pixels, so the room looks identical. A highlight or a slight scale-up pulse never reveals a hole. Feedback must not **move or shrink** a sprite, because the original painted object underneath would show.
- **Cut-outs** are made by applying the resolved mask to the painting (about 1 px of edge feathering from a 3 × 3 blur of the alpha), trimming to the bounding box plus 1 px, and packing into the atlas with a shelf packer. Their position comes from the mask's bounding box. `?debug=cutouts` (dev and test builds) hides the painting to check that every cut-out sits in place.
- **The hit map is the single authority for taps.** Each pixel of the hit map holds the index of the instance that owns it, or 0 for none. One lookup per tap answers *which object was touched*, with no rectangles, no overlap ambiguity, and no dependency on draw order.
  - Stored at **half resolution** (1024 × 768, ~0.75 MB as bytes in memory), read once at room load into a `Uint8Array`. Up to 255 instances per room.
  - **File format:** `hitmap.bin` is **run-length encoded**: little-endian Uint16 pairs `[value, count]` covering the pixels in row-major order (~18 KB for the M1 kitchen). A binary file is used instead of a PNG so that no browser colour management can alter the index values, and so the decoder is a pure function testable in Node (`src/core/hitmap.js`).
  - **Overlaps are resolved at build time.** Masks may overlap (hand-made masks usually cover an object's whole shape). Contested pixels go to the object with the higher manifest `depth`; at equal depth (default 0) the smaller object wins (a cup in front of a cabinet). Every overlap is reported as a warning with its pixel count and winner. The cut-outs use the resolved regions too, so a back object's cut-out never includes the object in front.
  - **Hit regions are padded.** Every region grows by 8 logical px into free (unowned) pixels, so thin parts such as chair legs are easier to hit, plus any per-object `hitPadding` from the manifest. Regions still smaller than the minimum tap size (80 logical px, §5) keep growing until they reach it, never into another object; a warning lists any that cannot. Tap points are computed before padding, so they stay inside the painted object.
- **Tap points:** for each instance, the build computes a point guaranteed to be well inside its hit region (the point farthest from the region's edge, nearest its centroid on ties). Tests tap there, and *Look and identify* can anchor its highlight there.

### Separation of Concerns

| Artifact | Owned by | Contains |
|----------|----------|----------|
| **Lexicon** (`content/lexicon.json`) | Content | One entry per English word: stable ID, display label, prompt text, accepted spellings, audio references. Shared by all rooms. |
| **Room manifest** (`content/rooms/<room>/manifest.json`) | Content | Room ID and title, the list of lexicon IDs used in the room, and optional per-object settings (difficulty, eligible activities, `depth` override, extra hit padding). |
| **Room art sources** (`content/rooms/<room>/room.png`, `masks/`) | Content | The painting and one mask per instance. **Mask file names carry the object ID.** |
| **Generated room assets** (`public/assets/rooms/<room>/`) | Build | Background, atlas, hit map, layout. Never edited by hand; not committed (rebuilt by `build:rooms`). |

Art can change without touching rules, and vocabulary can change without touching code.

### Rules

- **Keep object IDs stable** across lexicon, manifests, mask file names, audio files, and tests. IDs are lowercase kebab-case English (`refrigerator`, `coffee-table`).
- **Mask file naming:** `masks/<objectId>.png`. For several instances of the same object, use `masks/<objectId>@1.png`, `masks/<objectId>@2.png`, and so on (e.g. four chairs). Tapping any instance is correct.
- **Anything without a mask is not interactive.** Walls, floor, and decorative details can never register as answers.
- **Avoid hardcoding screen coordinates** in learning logic. Logic only ever sees object IDs.
- **Prompt text is stored, not generated** (*"Find the scissors"*, *"Find the rice"*), which avoids article and plural mistakes.

### Example Data


### Proposed Gameplay Rules

These are proposed defaults, to be confirmed (see §11):

- **Round length:** 10 challenges, drawn without repetition from the room's eligible objects; no word repeats within a round while unused words remain.
- **Wrong answer:** encouraging feedback and another try. After **2 wrong attempts**, the game **reveals** the answer (highlights the object and plays its word), then moves on.
- **Scoring:** a challenge counts as *correct* if answered without a reveal. The HUD shows *correct / attempted*, with optional elapsed time.
- **Look and identify:** 3 or 4 choices; distractors come from the same room and never share an accepted spelling with the answer.
- **Recall and spell:** the answer is trimmed, lowercased, and has repeated spaces collapsed, then compared against `accepted`. Typo tolerance is a later enhancement.

## 5. Content Creation Workflow

1. **Define** the room's vocabulary: add new words to the lexicon (reusing existing IDs) and list them in the room manifest.
2. **Paint** the room with AI image generation at **2048 × 1536**, following a shared **style guide** (palette, line style, lighting, camera angle) and a reusable prompt template that names the room's objects.
3. **Review and fix** the painting: every manifest object must be present, recognizable, and not hidden. Use **inpainting** to add, replace, or fix individual objects rather than regenerating the whole room.
4. **Mask** each interactive instance, using a segmentation tool (click the object to get its outline, then clean up) or a layer per object in an image editor. Export each mask as `masks/<objectId>.png` at the painting's size.
5. **Build** the room with `npm run build:rooms`. It produces the background, atlas, hit map, and layout, then reports problems: missing or extra masks, overlaps, regions too small, empty masks.
6. **Check** `reports/rooms/<room>-debug-hits.png`, or run the game with `?debug=hits` to show colored hit regions over the room; fix masks and rebuild until correct.
7. **Generate audio** with the TTS script: it reads the lexicon, produces the word and prompt clips plus shared feedback clips, normalizes loudness, and writes MP3s. Generated files are committed, so the build never calls a TTS service.
8. **Validate** with `npm run validate:content` (also run in CI, see §8).
9. **Preview** in a desktop browser (and on the iPad from M5), run the interaction tests, and repeat until acceptable.

> **Realistic expectation:** a single AI-generated image rarely contains 50 correct, distinct objects on the first try. Expect to start with a strong base painting and add objects through inpainting. The manifest's object list is the checklist.

### Interaction and Layout Guidelines

- **Minimum tap size:** sized for a child's finger on the iPad, about **44 × 44 pt** on screen, roughly **80 × 80 logical pixels** at 2048 px width on common iPads. Applied from the start, so rooms need no rework when iPad support arrives. The build pads smaller regions up to this size where free space allows and warns where it cannot.
- **Logical resolution:** a fixed design canvas of **2048 × 1536** (4:3, matching iPad Retina proportions), scaled with Phaser's `Scale.FIT` and centered. On a 16:9 or 16:10 laptop screen this leaves bars on the sides, which the shell can use for the HUD. Keep interactive objects inside a safe area so letterboxing crops nothing important.
- **Highlight and feedback:** a coloured glow around the object, plus a gentle scale-up pulse (at most about 24 logical px) and sounds. No moving or shrinking (§4).
  - The glow is a **white halo built by `build:rooms`** for each instance (opaque over the object, fading to clear 24 px from its edge), packed in the atlas next to the cut-out. The game tints it (green: correct, orange: try again, yellow: reveal) and draws it behind the cut-out, which sits exactly over the painted object.
  - Phaser 4's runtime glow filter was tried first and rejected: each filtered sprite cost about 1.7 s to set up in software WebGL (CI), and a shared filtered container slowed every frame. Build-time halos cost nothing at runtime and behave the same on every device.
  - On the Canvas renderer (no tinting), feedback falls back to a tinted overlay of the hit region.
  - The reveal ring surrounds small objects so it never hides them, and sits on the tap point of large ones.

## 6. Performance and Multi-Room Support

Twelve rooms with around fifty objects each is easy for a laptop and a reasonable target for a modern iPad browser, **provided assets are sized sensibly**. The iPad is the constrained device, so budgets are set for it.

The main constraints are:

- **Decoded image memory:** every texture costs width × height × 4 bytes in memory, whatever its file size. A 2048 × 1536 background costs about 12.6 MB; the cut-out atlas adds roughly the area the objects cover.
- **Download size**
- **Texture dimensions:** keep each atlas page at **2048 × 2048 or below** (4096 × 4096 at most).
- **Audio caching:** decoded audio is stored uncompressed in memory.

The raw number of vocabulary entries is **not** a constraint, and hit testing costs one array lookup per tap.

### Initial Budgets (to confirm on the iPad in M6)

| Item | Target |
|------|--------|
| Room background | 2048 × 1536 WebP, ≤ 600 KB |
| Room object atlas | 1–2 pages of ≤ 2048², ≤ 1.5 MB total |
| Room hit map | 1024 × 768, run-length encoded `hitmap.bin`, ≤ 100 KB; ~0.75 MB in memory |
| Room audio | ~100 short mono MP3 clips (64–96 kbps), ≤ 1.5 MB |
| Room switch time (cached) | ≤ 1 s |
| Room first load on Wi-Fi | ≤ 3 s |
| Tap-to-feedback latency | ≤ 100 ms |

### Recommended Strategy

- **Load one room at a time** rather than loading every room into memory.
- **Preload shared assets** (UI, feedback sounds, fonts) once at boot.
- **Preload the current room's essential assets** behind a short loading indicator; optionally prefetch the next room's files into the HTTP cache.
- **Release unused room-specific textures, hit maps, and audio** when leaving a room (`textures.remove`, `cache.audio.remove`). The browser HTTP cache avoids re-downloading them on return.
- Consider a **per-room audio sprite** if the number of HTTP requests becomes a problem.
- **Test on the target iPad**: load time, memory use (Safari Web Inspector), and touch responsiveness.

## 7. Browser and iPad Considerations

### All Browsers (from M1)

- **Pointer input:** use Phaser's pointer events only, never mouse-specific or touch-specific handlers, so clicks and taps share one code path.
- **No hover-only behavior:** nothing the child needs may depend on hovering, because touch screens have no hover.
- **Audio unlock:** desktop browsers and iPadOS Safari both block audio until a user gesture. The **Start** button is that gesture, and Phaser unlocks its sound manager on it (M3). Show a visible prompt so the child always clicks or taps before the first challenge.
- **Spelling input:** a DOM `<input>` overlaid on the canvas, typed with the physical keyboard on a laptop/PC.
- **Window resizing:** the canvas rescales with the window (`Scale.FIT`); the shell layout follows.

### iPad (from M5)

- **Silent mode:** Web Audio can be muted when the iPad is silenced. Show a small "sound on?" hint on the start screen.
- **Touch behavior:** prevent zoom, scrolling, text selection, and the long-press callout over the game:
  - viewport meta with `user-scalable=no`
  - CSS `touch-action: none`, `user-select: none`, `-webkit-touch-callout: none`
  - `overscroll-behavior: none`
- **Orientation:** landscape only. In portrait, show a "rotate your iPad" overlay.
- **Full screen:** optional. *Add to Home Screen* with a web app manifest (`display: standalone`) removes the Safari toolbar. No service worker or offline mode in the initial version.
- **Spelling input on the on-screen keyboard:** give the `<input>` `autocomplete="off"`, `autocorrect="off"`, `autocapitalize="off"`, and `spellcheck="false"`, so iPadOS does not autocorrect or suggest the answer. The on-screen keyboard covers the lower part of the screen, so the highlighted object and input must stay visible above it. A custom in-game letter keyboard is an alternative (§11).
- **Speech recognition** (*Speak the word*, future activity) is out of scope. Browser speech recognition support on iPad Safari is limited and should be evaluated separately.

## 8. Testing and CI

### Test Layers

| Layer | Tool | Scope |
|-------|------|-------|
| **Unit** | Vitest (Node) | Seedable RNG and shuffling, question selection (no repeats, eligibility, difficulty), distractor selection, answer normalization and checking, retry/reveal rules, scoring and session state, **hit-map lookup and coordinate conversion**, and room-build algorithms (overlap resolution, padding, tap points) on small synthetic masks. |
| **Content** | `tools/validate-content` + `build:rooms` checks (Node + Ajv) | See below. |
| **End-to-end** | Playwright | Full rounds in desktop Chromium from M1; WebKit with an iPad profile added in M5. Runs against the production build served by `vite preview`. |
| **Manual** | Laptop/PC browser, then real iPad | Per-milestone checklist in a desktop browser from M1. From M5, also on the iPad: audio, touch accuracy, memory, orientation, keyboard. Playwright WebKit on Linux is **not** a substitute for iPad Safari. |

### Content Validation

- Lexicon and manifests match their JSON Schemas (required fields, types, ID format).
- IDs are unique; every manifest object exists in the lexicon.
- Every manifest object has at least one mask, and every mask file name matches a manifest object.
- Masks have the painting's dimensions and are not empty.
- Mask overlaps are reported (resolved by size or `depth`). Regions below minimum tap size that cannot be padded are warned about.
- Every lexicon audio reference exists.
- Accepted spellings are lowercase and do not collide between objects in the same room.
- Warnings (not failures) for unused assets.

### Test Bridge

- Enabled only in the **test build** (`npm run build:test`, i.e. `vite build --mode test` into `dist-test/`), which `npm run test:e2e` builds and serves. It is **stripped from production builds** (`import.meta.env.MODE` is replaced at build time, so the code is removed). The `?debug=hits` overlay follows the same rule (dev and test builds only).
- Exposes `window.__wordsTest` with:
  - the current challenge's object ID
  - each instance's **tap point**, converted to screen coordinates (from the generated layout, never hardcoded)
  - the last played audio key
  - a way to set the RNG seed
- Playwright **performs a real tap at the tap point**, so the real input pipeline (scaling, coordinate conversion, hit map) is exercised without brittle pixel coordinates.
- Audio is asserted through the last played key, not by listening.

### Example End-to-End Case

> Start with seed `42` → open **Kitchen** → read the current target (`refrigerator`) from the bridge → tap the refrigerator's tap point → assert that the HUD counter reads **1 / 1** → tap a wrong object on the next challenge → assert *try again* feedback and **1 / 1** unchanged.

### GitHub Actions Pipeline (`.github/workflows/ci.yml`)

Triggered on **push** and **pull request**:

1. Check out the code; set up Node LTS with the npm cache.
2. `npm ci`
3. `npm run lint`
4. `npm run validate:content`
5. `npm run test` (Vitest)
6. `npm run build` (runs `build:rooms` first, then the Vite build)
7. `npx playwright install --with-deps chromium` (plus `webkit` from M5)
8. `npm run test:e2e` (starts `vite preview` and runs Playwright)
9. On failure, upload the Playwright report, screenshots, traces, and `reports/` (room review images) as artifacts.

Canvas screenshot comparisons are **not** a pass/fail gate at first, because rendering differs across platforms. Screenshots are captured for review; visual baselines can be added later for a few stable screens.

## 10. Implementation Plan

Each milestone ends with a **demo in a laptop/PC browser** (and, from M5, **on the real iPad**) and **green CI**. Milestones are sequential. Content production (M2, M7) can overlap with code work once the pipeline exists.

The order aims for a **playable room as early as possible**: M1 delivers a text-only *Listen and find* round in a desktop browser (the prompt is displayed, the child clicks the object). Art quality, the full room pipeline, audio, the other activities, and iPad support are added on top of that working game.

### M0: Project Setup

> **Status: done.** See the [M0 completion report](docs/milestones/M0.md).

- Create the Vite + Phaser 4 project from Phaser's official template, with ESLint, Prettier, Vitest, and Playwright (Chromium).
- CI workflow running lint, unit tests, and build.
- Project structure (§9) with placeholder folders.
- **Exit:** the repository builds in CI, and an empty Phaser canvas displays and rescales with the window in a desktop browser.

### M1: First Playable Room (Kitchen, text-only Listen and Find)

> **Status: done.** See the [M1 completion report](docs/milestones/M1.md).

- **Placeholder kitchen:** one AI-generated kitchen painting and about **8–10 masks** made by hand in any image editor. No tool evaluation or style guide yet.
